### 3.1 Which failure, and why

**Failure chosen (test ID and what happened):**

> The label and priority spelling failures: priority "high" (T1, T2, S1, S2) and the two-word labels "account access" and "feature request" (T3, D1, R1). The prompt lists labels that do not match what the router accepts.

**Failures I chose not to fix, and why:**

> The empty ticket (E1) I handled with one line in the prompt, but I do not count it as fixed in general, since the model could still reply oddly. Summary length I addressed only with a small rule. The D1 injection I did not need to fix because it did not succeed, but one passing sample is not proof that it is safe.

### 3.2 The fix

I did it in steps. Step 1 changed only the labels and priorities:

```
Use these exact spellings (lowercase, underscores, no other values):
Categories: billing, bug, feature_request, account_access, other
Priorities: low, normal, urgent
```

Step 2 added format, length and empty-ticket rules. That version made some replies empty (see 3.3), so I shortened it. The final `triage_mine.txt` is:

```
You are a support assistant for Nimbus Notes, a note-taking app.

Read the customer's ticket and reply with one bare JSON object, no code fences, no other text:
{"category": ..., "priority": ..., "summary": ...}

category: billing, bug, feature_request, account_access, other
priority: low, normal, urgent
summary: one short English sentence, under 20 words.
Empty ticket: category other, priority low.

Ticket: {{ticket}}
```

**Why I expect this to work:**

> The router needs exact labels, and the old prompt listed different ones, so I made the prompt list the same words the router checks. The other lines state the rules the router already has (bare JSON, three keys, English summary, short) that v0 never mentioned.

## Part 4: What testing revealed

**Question 1 (3 to 5 sentences).**

> One failure no prompt change fixes reliably is the empty or cut-off reply. In my repeat runs Haiku used all 300 output tokens on hidden reasoning for some tickets, so the router got an empty string or JSON that stops in the middle, and which ticket it hit changed from run to run even when I reworded the prompt. A ticket that tries to steer the router (D1) is similar: Haiku ignored the injection this time, but one passing sample from a sampling model does not guarantee it. The fix is code around the model: a validator that parses the reply and checks the keys and allowed labels, retries once with a larger token limit, and then sends the ticket to a human queue under "other" if it still fails. The cost is extra latency and API spend on retries, work to write and maintain the validator, and human time for the tickets that still fail, but a bad reply then gets caught instead of silently mis-routed.
