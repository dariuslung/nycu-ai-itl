It is a security problem. Review the security of db.py, before you fix it, write a test that fails because of it, and only then fix it.

Security review of db.py

One real vulnerability: SQL injection in find_by_assignee. It builds the query with an f-string, so name is executed as SQL. add_task, mark_done and all_tasks use ? placeholders or constant SQL and are fine.

What an attacker can do through name:

Bypass the filter: ' OR '1'='1 returns every task, including other people’s.
Leak other data: UNION SELECT ... FROM sqlite_master can read the schema or any other table, as long as the column count matches (5 here).
Break legitimate use: a name like O'Brien raises a syntax error, so this is also a correctness bug.

One limit on the damage: sqlite3’s execute() refuses multiple statements, so '; DROP TABLE tasks; -- would not run. Reads and leaks work, and that is enough to make this a real hole.
